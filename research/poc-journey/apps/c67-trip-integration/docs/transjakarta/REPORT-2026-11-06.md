# TransJakarta itinerary POC — 6 November 2026

## Outcome

Trip Integration now offers an explicit TransJakarta BRT plus walking transport choice and carries it through recommendation, location review, route generation, revision, acceptance, persistence and export. The POC covers direct corridor-1 journeys between Bundaran HI and the Blok M area. The existing routing optimizer selects BRT or walking for each leg within that choice.

The bus component uses published GTFS Schedule data. Access, egress and local walking use native MapKit. WeatherKit supplies weather on the signed iPhone. Runs are labeled `live_gtfs_estimate`, and authored walking/search/weather replay uses `synthetic_replay`.

## Data and explicit assumptions

The official ZIP was retrieved on 6 November 2026. Its Last-Modified header was `Fri, 30 Oct 2026 09:51:57 GMT`. The ZIP SHA256 was `376b11f72ac30f9f4eb972ae32c7f1a3251b416dc3cd77cc573475a3b2676b9c`. The imported subset contains route `1`, agency `Tije`, category `BRT`, 18 trip patterns and 59 boarding stop records. It retains parent/platform identity, weekly calendars, ordered stop occurrences, frequencies and the original source attribution. The importer normalizes stop-time offsets relative to the first departure and omits shapes and fares. The bundled JSON matched a fresh transformation of the captured ZIP. [Official feed](https://gtfs.transjakarta.co.id/files/file_gtfs.zip) · [Publisher attribution](https://ppid.transjakarta.co.id/informasi/berkala) · [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

Every corridor-1 frequency in the snapshot uses `exact_times=0`. The POC uses one full headway as a waiting buffer after the passenger reaches the boarding coordinate or service starts. Bus duration is the difference between the chosen boarding departure offset and later alighting arrival offset. Ordered occurrences preserve loop patterns with repeated stop IDs. Published frequency windows use an exclusive end. The runtime considers both the current and previous service day for after-midnight service. [GTFS frequency reference](https://gtfs.org/documentation/schedule/reference/#frequenciestxt)

Implementation defaults were selected for this bounded experiment.

- Direct corridor-1 service and local walking. Transfers are deferred.
- At most two nearest published boarding coordinates within 800 m of each endpoint.
- At most 20 minutes for each access, egress or direct walking component. A 2 km geographical gate bounds direct-walk discovery before requesting MapKit.
- At most 128 native walking requests per calculation, paced at 1.2 seconds. Coordinate pairs are cached within a calculation.
- A snapshot must have been checked within seven days of planning. Refresh requires rerunning the importer and rebuilding.
- Weekly calendars are retained. The feed has no `calendar_dates.txt` exception table. A future exception table or unsupported pickup/drop-off restriction stops import for review.
- The transport choice applies to one request. The report compares separately generated car and busway requests using the same three selected places.

The UI and exports show walking, boarding/alighting platforms, published direction/headsign, GTFS waiting buffer, bus running time, source date and license. `travelMinutes` includes all transport components. The existing `waitingMinutes` metric describes waiting for a venue visit window, so bus waiting is also reported separately in journey evidence.

## Failures and corrections

The first device launch was rejected while the iPhone was locked. The user unlocked it and the installed app launched successfully. The first live run produced a valid one-place busway itinerary and a valid three-place car itinerary. During the three-place busway case, a walking request exceeded the cooperative 25-second timer and the case eventually finished in about 300 seconds. That partial run was preserved before replacing the build.

The walking adapter now owns a checked continuation and resolves it on response, timeout or cancellation. Request identity discards late callbacks. Regression tests exercise a missing callback, late callback, explicit cancellation and task cancellation. The original run is retained under `device-original-run/` and its progress logs remain available.

After evaluation, a final signed build with isolated interactive busway session storage was installed successfully. The final attempt to open `--p3-busway` was rejected because the iPhone had locked again. The recorded device evaluation and Simulator review/acceptance results had already completed. The interactive handoff launch on the physical phone remains unobserved.

The first UI run passed the nine Foundation Lab checks and two Trip Integration checks. Two Blok M flows failed because the helper asserted a lazily created proposal button existed before scrolling. The helper now uses its existing scrolling action to reach that button. The failed result bundle is preserved under `ui/C67TripIntegration.xcresult`.

## Remaining limits

Actual boarding, stop entrance and crossing access, accessibility, crowding, real headways, disruption handling, field arrival accuracy and manual network/background/input-change observations remain untested. GTFS coordinate access may differ from a usable station entrance. Bus arrivals and traffic are estimates from the published schedule snapshot. Holiday exceptions, transfers, fare optimization and route geometry need additional work. The route search remains bounded and heuristic.

## Reproduce

From the repository root, run the deterministic package checks and explicitly choose a new output directory for each replay.

```sh
rtk proxy bash poc-journey/scripts/verify.sh packages
rtk proxy swift run --package-path poc-journey/apps/c67-trip-integration/Packages/TripIntegration p3-blok-m-eval --out NEW_DIRECTORY --baseline --replay --busway
```

The interactive `--p3-busway` launch uses separate `Application Support/C67Busway-2026-11-06` session storage.

Use Debug launch argument `--p3-busway-replay` for the synthetic UI flow, `--p3-busway-live-eval` for the isolated signed-device evaluation, or `--p3-busway` for interactive Blok M input with busway selected. Live evaluation artifacts are written to `Documents/P3BuswayEval/<run UUID>`. Export from the review screen to obtain the JSON, Markdown, native report and provider log.
