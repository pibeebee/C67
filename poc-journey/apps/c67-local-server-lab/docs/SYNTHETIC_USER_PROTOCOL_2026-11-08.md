# Synthetic user evaluation — frozen protocol

Three authored personas are frozen in `artifacts/synthetic-user-2026-11-08/frozen-briefs.json` before new recommendations. Each is an imagined user desire, not a statement about Giovan. The assistant both authored and evaluates the personas and knows the implementation; this is not a blinded human evaluation or independent LLM judge. No AnyJev integration is included.

Evaluate the existing app first, without algorithm/prompt tuning. Record (1) what the UI can express, (2) returned candidate fit and missing evidence, (3) inspect/select/identity friction, (4) itinerary compliance, (5) whole-desire verdict. Missing evidence is unknown, never proof of absence or presence. Do not invent amenities, access, prices, vegetarian menus, quietness or indoor status from venue names. Source types support only coarse activity categories. A known opening window is not last-entry/ticket validation.

Use the Simulator with real E5 and mandatory free LLM, the same local provider APIs and a separate synthetic test profile. Preserve the normal user's state. Freeze Tuesday 10 November 2026. U1: reading/coffee, Cikini Menteng, 10–16, 90/45-minute dwell. U2: arts/architecture, Kota Tua, 13–19, 60/45 minutes, photography start15–16 when expressible. U3: food/shopping, Blok M, 11–16, 60/60 minutes. All permit automobile/return-to-origin and a maximum15-minute total wait. Synthetic users author these constraints; none is inferred from pace.

Inspect every returned candidate. Primary category is required; a supported secondary is optional. Choose by source-supported activity first, hours second, then independently confirmed Apple venue identity; record rejected identity matches. A plan built with unresolved venue suitability is a technical diagnostic, not an accepted trip. Do not force unrelated substitutions to obtain a passing itinerary. At most one explicit recommendation retry per persona; failed attempts count separately. Freeze selections after observing the list but before route results. No repeated routing parameter tuning to improve verdicts.

Recommendation latency is submit-to-first-card; route latency starts after preparation. Timing is descriptive (one persona run per case), not a speedup benchmark. Report unknowns, not-expressible criteria, supported/contradicted requirements, conditional/rejected plans and non-reached phases separately. No synthetic "accuracy percentage" or population claims. New harness mistakes may be fixed with dated amendments, without rewriting briefs or hiding attempts.
