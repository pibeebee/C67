# Hybrid v4 integration checkpoint

The Swift `V4Planner` ports the finite-domain generator, evaluator, candidate families, shortlist, exact-time quote cache and ranking from `poc/hybrid-v4-lab/v4_planner.py`. The app requests one Luna experience recommendation, builds a static first-departure MapKit proxy for directed legs, screens its declared order/departure/wait domain, and validates up to five selected schedules with departure-specific MapKit quotes. The app uses the prototype's compact-day objective. The proxy consumes its own route requests and is not an established forecast of later traffic. Actual quote validation has an experimental 72-call cap; neither number is an Apple allowance. Throttling stops the search. Search is limited to at most six stops and 100,000 finite candidates; the adapter coarsens its explicit departure/wait grid to remain within this bound. This can miss a valid or better itinerary, and no global optimum is claimed.

Native input mapping preserves user-first/last and locked order, confirmed visit access, provider regular hours (subject to special-date uncertainty), unknown/error hours, Luna duration estimates, user duration overrides, user hard/soft visit-start timing, allowed total wait, endpoint and deadline. Multiple or overnight provider windows are normalized and touching windows merged. Timestamps are rounded to minute precision, with arrival duration rounded up. The current UI exposes only the total waiting allowance, so the adapter uses the same value for the prototype's per-stop limit. Unknown duration or missing ETA cannot create a complete recommendation. Model-suggested day-part is not converted into a time target. Weather exposure, last-entry, activity sessions and live adaptation remain outside the implemented product data mapping; do not claim they were optimized.

`V4Replay.json` and `V4ExhaustiveReplay.json` are reduced exports of the two Python benchmark runs in the workspace. The Swift tests replay all 17 bounded cases and compare every evaluated schedule, selected result, candidate count, quote count, and budget state byte-for-byte after canonical JSON encoding. Exhaustive replay compares recommendation, candidate count, quote count and budget state for all 17 cases. These synthetic parity checks do not establish live MapKit accuracy or human preference quality. A repository test separately checks all 120 orders for five selected places, unknown access warnings, and final return.

The iPhone exposes Luna, Hybrid weather (v2), and experimental Hybrid v4; the retired v1 enum remains decodable for old jobs and a saved v1 choice is migrated to v2. The Pocket server accepts `hybrid_v4` and requests an unrestricted Luna experience recommendation; scheduler code runs on the device. The deployed server image remains `c67-pocket-beta-pocket:v4-20261117`; no new server change was necessary for the native scheduler replacement. The previous `hours-20261117` image and existing data volume are retained. Health and request parser were checked previously. A successful authenticated end-to-end itinerary using live Luna, live MapKit and a physical iPhone has not yet been established, and the app has not been uploaded to TestFlight for this change.

## Automatic date for the first itinerary

In a new automatic V4 draft, the first attempt uses the remaining day in the trip time zone, with a ten-minute lead time. The default fallback window is 09:00–23:59 tomorrow. V4 attempts that window if the planned visit durations already exceed today's window or every candidate in the finite search was evaluated and missed the deadline. Anchor dates use the stored job creation time so retries keep the same request dates and identities.

Editing the time window fixes the selected date. In **Adjust schedule**, **Trip date** moves both endpoints of the window to the selected day, with separate departure and finish time controls. A proven time conflict on an explicitly selected today offers **Try tomorrow**. Dated visit confirmations and visit targets keep their date. Missing quotes, a shortlist miss, and throttling cannot by themselves trigger a date change. The automatic retry refreshes context and route estimates for tomorrow and keeps the stops and user-set durations. It may make a second Luna request if the first attempt already obtained a recommendation. Review shows why the date moved and saves the proposal on that date.

Four targeted Swift package tests passed. Two app integration tests in `TripCreationTests.swift` passed on the iPhone 18 Pro Max Simulator (iOS 27.2) using the real presenter and Pocket repository with synthetic providers and a fixed Jakarta clock. The automatic case checks the review date, the stored job, and the trip restored from disk. The manual case checks that today remains selected until the presenter handles **Try tomorrow** and creates a new request. When filtering individual Swift Testing methods with Xcode, include the trailing `()` in the method identifier and check the executed test count in the result bundle.

Two XCUITests passed on the same simulator. One opens the date and time controls from the main spot screen and reaches the Hybrid v4 itinerary. The other sets the synthetic repository's job clock to 23:30 Jakarta time and verifies the automatic reschedule explanation, both selected places, and the review's save-for-later action. These runs used synthetic providers. The separate lab run produced no recorded results, and physical-device verification remains pending.
