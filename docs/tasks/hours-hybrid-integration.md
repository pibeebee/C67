# Opening-hours integration for Pocket

Status: implementation in progress. Preserve the authenticated Pocket path and PR #28 UI; do not change the local Xcode scheme. The independent Apple hours source is optional, server-side, and must not store credentials or raw Apple hours in long-lived job/snapshot storage. Keep missing hours unknown; category hints are unverified soft preferences, never hard opening or closure claims. User-selected places and order locks are retained. Cinema 10:00–02:00, mall 10:00–22:00, and museum 09:00–16:00 are uncalibrated hypotheses, not venue facts or film schedules. Explicit correctly scoped hours take precedence. Request-time and post-route comparisons require departure, travel estimates and visit durations; do not substitute straight-line distance or invented values for road ETA. Cross-midnight windows, local timezone, holidays/special date uncertainty, error vs no data, token secrecy, retry limits, and old job backward compatibility require focused tests. Server deployment is a separate reviewed action.

## Implemented locally and remaining work

The authenticated lookup returns transient, validated weekly records or an explicit unavailable/error status. The itinerary review compares available regular hours with its existing estimated visits and labels category-only hours as unverified. Hybrid Weather receives category hints during Luna ordering. After that response, the device can fetch place-specific hours and compare the original route with up to five adjacent swaps using route quotes and available visit durations. Only a strict reduction in regular-hours conflicts changes the order. Locked orders and first-place constraints are preserved; unknown hours, missing route quotes, or unknown visit durations never become facts. Comparison is limited to two through six stops and does not apply waiting or date-specific exceptions. The default departure time is an estimate, not a user-confirmed schedule. The cinema interval is an experimental assumption, not screening or venue hours. A deployed/configured server, live provider verification, special-date coverage, and an end-to-end comparison of candidate schedules remain necessary before claiming the requested engine behavior is complete.
